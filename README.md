# AdRobot - Keitaro Control Plane

AdRobot — это промежуточный слой (BFF) для управления рекламными кампаниями в трекере Keitaro. Система предоставляет удобный графический интерфейс для создания кампаний, управления потоками (Flow), распределения весов офферов и двусторонней синхронизации с Keitaro Admin API.

Приложение спроектировано по принципам чистой архитектуры (Clean Architecture), использует асинхронный стек технологий и полностью контейнеризировано для быстрого развертывания.

## Технологический стек

Бэкенд:
- Python 3.12
- FastAPI (REST API)
- SQLAlchemy 2.0 (асинхронный ORM)
- Alembic (миграции базы данных)
- PostgreSQL
- Pytest (юнит-тестирование)

Фронтенд:
- React 18
- TypeScript
- Vite
- Ant Design (UI-компоненты)
- TanStack Query (управление состоянием и кэширование)
- Axios

Инфраструктура:
- Docker и Docker Compose
- Nginx (Gateway: раздача статики фронтенда и проксирование API)
- GitHub Actions (CI пайплайн)

## Особенности бизнес-логики

1. Двусторонняя синхронизация. Keitaro является ведущим источником данных. При нажатии кнопки Fetch from KT система запрашивает актуальные данные из трекера, подтягивает новые офферы, удаляет отсутствующие (помечая их статусом deleted in KT) и синхронизирует веса.
2. Режим редактирования (Draft Mode). Любые изменения в интерфейсе не отправляются в Keitaro мгновенно. Они копятся в локальной базе данных. При наличии несохраненных изменений UI подсвечивает страницу желтым фоном и показывает предупреждающий баннер. Отправка происходит только по кнопке Push to KT.
3. Умный пересчет весов. Алгоритм распределения весов (WeightAllocator) гарантирует, что сумма весов всех активных офферов всегда равна 100%. Если вес оффера закреплен (is_weight_fixed), он остается неизменным, а оставшийся процент автоматически и пропорционально распределяется между свободными офферами.
4. Soft-delete и Rollback. Если оффер удаляется в интерфейсе, он не стирается из базы физически, а помечается как удаленный. Это позволяет в один клик восстановить его (Rollback) с автоматическим пересчетом весов, либо отправить изменения в Keitaro.
5. Версионирование. При каждом успешном пуше в Keitaro создается снапшот (версия) состояния кампании, что позволяет отслеживать историю изменений.

## Переменные окружения

Перед запуском скопируйте `.env.example` в `.env`. Конфигурация содержит следующие переменные:

| Переменная | Описание |
|------------|----------|
| `POSTGRES_DB` | Имя базы данных PostgreSQL |
| `POSTGRES_USER` | Пользователь базы данных |
| `POSTGRES_PASSWORD` | Пароль базы данных |
| `DATABASE_URL` | Строка подключения к БД (для SQLAlchemy asyncpg) |
| `KEITARO_API_URL` | Базовый URL Admin API Keitaro (например, `https://your-domain.com/admin_api/v1`) |
| `KEITARO_API_KEY` | Ключ доступа к API Keitaro |
| `KEITARO_MOCK` | Если `true`, система работает в режиме эмуляции без реальных запросов к Keitaro (удобно для тестов) |
| `GOOGLE_REDIRECT_URL` | URL, на который будет перенаправлять трафик первый (редиректный) поток |
| `CORS_ORIGINS` | Разрешенные источники для CORS-запросов |

## Инструкция по запуску

Для запуска проекта вам потребуется установленный Docker и Docker Compose.

1. Склонируйте репозиторий на локальную машину.
2. Перейдите в корневую директорию проекта.
3. Создайте файл конфигурации окружения:
   ```bash
   cp .env.example .env
   ```
4. При необходимости отредактируйте `.env` (например, укажите реальные данные для подключения к вашему Keitaro).
5. Запустите сборку и старт контейнеров:
   ```bash
   docker compose up --build -d
   ```

После успешного старта будут доступны:
- Пользовательский интерфейс: `http://localhost:8080`
- Swagger UI (Документация API): `http://localhost:8080/docs`
- OpenAPI схема: `http://localhost:8080/openapi.json`

## Миграции базы данных

В проекте используется Alembic. Миграции применяются автоматически при старте Docker-контейнера бэкенда (в `Dockerfile` прописана команда `alembic upgrade head` перед запуском сервера).

Если вам необходимо создать новую миграцию при изменении моделей SQLAlchemy, выполните следующие команды из директории `backend` (предварительно активировав виртуальное окружение с зависимостями):

```bash
alembic revision --autogenerate -m "описание изменений"
alembic upgrade head
```

## Тестирование и CI/CD

Проект покрыт модульными тестами, которые проверяют логику распределения весов и работу сервисов с моками базы данных.

Для локального запуска тестов:
```bash
cd backend
pip install -r requirements-dev.txt
pytest
```

В репозитории настроен пайплайн GitHub Actions (`.github/workflows/backend-ci.yml`). При создании Pull Request в ветку `main` автоматически запускаются линтер (Ruff) и тесты (Pytest). Мерж в ветку `main` блокируется в случае падения тестов.
